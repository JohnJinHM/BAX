# BAX 断箭辅助工具项目规划

日期：2026-11-16（America/Los_Angeles）  
阶段：需求整理与可行性验证

BAX 面向《Broken Arrow／断箭》，提供对局悬浮窗、计时提醒、玩家档案与备注、历史风格统计和战后单位分析。数据链路采用本机游戏日志识别对局，优先通过游戏数据源获取玩家基础资料与战报，由 BATrace 补充和回退，并保存为本地长期记录。数据源方案于 2026-11-21 更新，见 [ADR-0015](../adr/0015-primary-source-with-batrace-fallback.md)。

## 已确定事项

- 单独建立项目，以 BA-ELO-Overlay 原型为基础，已取得作者同意，可以复用其源码。
- 桌面技术暂定 Tauri＋Rust；前端框架和具体依赖在可行性验证后确定。
- 当前先完成规划和必要验证，项目开发另行启动。
- 首阶段排除反作弊、疑似作弊、小号及异常行为判定，以及相关标签、告警和检测详情页。
- 保留客观的出兵、击杀、损失、补给等统计，用于描述玩家风格。原型中的自动组排推断暂不纳入首版；个人备注独立保存。

## 产品范围

| 功能 | 目标行为 | 当前依据 |
|---|---|---|
| 对局悬浮窗 | 自动识别当前比赛、双方玩家，显示 ELO、等级、备注与简要画像 | 原型已有日志识别、查询和悬浮显示 |
| 展开详情 | 从紧凑窗口展开玩家摘要，完整档案与图表在主窗口查看 | 建议采用两个窗口，共享同一份后台状态 |
| 自定义皮肤 | 切换主题，调整颜色、透明度、字号与间距 | 网页前端支持统一样式变量 |
| 定时提醒 | 设置正式开局后第 10 分钟等提醒，支持取消与修改 | 日志与战报时间交叉核对支持候选计时方案 |
| 玩家档案 | 缓存资料，每次相遇刷新，保存备注和历史相遇记录 | 稳定玩家 ID 与 SQLite 可支撑 |
| 风格统计 | 常用单位、兵种构成、出兵节奏、占点和补给倾向 | 战报包含单位实例及玩家统计 |
| 专精统计 | 展示熟练度，进一步研究近期专精使用率 | 已有专精经验和等级，逐场专精选择待确认 |
| 战后分析 | 比赛结束后获取战报，展示各玩家出兵时间线和对比图 | 已实测完整比赛接口 |

窗口化和无边框全屏作为优先支持场景。独占全屏、多屏和不同 DPI 下的悬浮行为列入实机验证。

## 原型源码与复用方式

原型使用 Python、Tkinter、SQLite、urllib 和 threading，通过 ctypes 调用 Win32 实现托盘、快捷键和点击穿透，使用 PyInstaller 发布。主程序集中在 `src/ba_elo_overlay.py`，检测逻辑位于 `src/elo_cheat_check.py`。

| 原型位置 | 可复用内容 | BAX 处理方式 |
|---|---|---|
| `_steam_library_dirs`、`find_game_logs` | Steam 库与日志目录发现 | 移植到 Rust，保留手动指定路径 |
| `LogWatcher` | 日志事件、增量读取、历史重读标记 | 扩展为对局生命周期解析器 |
| `fetch_json` | 接口路径、JSON 检查、请求头与代理经验 | 迁移为统一 Rust API 客户端 |
| `EloService` | 玩家预取、并发查询、旧缓存回退、过期请求隔离 | 保留流程，调整刷新策略 |
| `Cache` | JSON 缓存形式与键命名 | 拆分短期缓存和长期档案 |
| `TrayIcon`、窗口相关方法 | 快捷键、托盘、锁定穿透、吸附等行为 | 用 Tauri 能力实现，必要时补充 Win32 |
| `elo_cheat_check.py` | 比赛列表查询、单位目录映射等数据处理思路 | 单独提取客观统计所需部分，检测规则及扫描流程排除 |
| Tkinter 界面、PyInstaller 打包 | 原型操作方式可作为参考 | 界面和发布流程按新技术栈组织 |

源码为 MIT 许可，版权声明为 `Copyright (c) 2026 BA-ELO-Overlay contributors`。复用代码或实质性改写其内容时，在新项目保留相应许可及来源说明。当前原项目保持原状，功能移除针对新项目范围。

### 移植时需要修正的行为

- 玩家名称正则当前使用 `(.+)`；真实日志中存在空名字，应先保留玩家 ID，再用接口资料补全名字。
- 日志读取需处理跨次读取的半行、UTF-8 字符边界、文件截断和新文件切换，并按比赛 ID 去重。
- 重读历史日志应恢复状态；提醒是否已经触发需要持久化，避免启动时补发过期提醒。
- 原型档案缓存为 24 小时；本项目要求每场动态更新，应先显示缓存，再按刷新策略更新。
- 原型 `Cache` 初始化会删除超过 7 天的记录。这一清理方式只适合缓存；玩家备注、相遇记录与已归档战报应独立保留。
- 当前 `Overlay` 同时调度界面、查询和检测。新项目将窗口展示与业务状态分开，由 Rust 统一维护数据。

## 数据来源与已验证能力

以下数值来自本次策划会话前序的只读检查与接口实测；本次文档整理额外核对了提供的源码。它们是样本结果，后续版本需继续验证。

### 游戏日志

本机路径：`C:\Program Files (x86)\Steam\steamapps\common\broken_arrow\GameLogs`。

| 日志内容 | 用途 |
|---|---|
| `WaitingRoom entered, fight id` | 获取比赛 ID，开始预取玩家信息 |
| `GameRoom entered` 与 `Player list` | 获取玩家 ID、名称和 Alpha／Bravo 队伍 |
| `Start loading battle... map` | 读取地图名称 |
| `Deck set to` | 本人卡组名称；名称可自定义，作为辅助信息 |
| `Scenario controller loaded` | 计时起点的候选事件 |
| `Cause=MatchEnded` | 触发战后获取与归档 |
| `Start reconnect to battle`、`Request reconnect data` | 识别重连，恢复原比赛状态 |

最近 12 份日志识别到 83 个不同比赛 ID。名单块包含 10 人及其他人数，解析器需兼容重复事件、重连和不同房间情况。

样本日志没有提供完整且可归属到每位玩家的单位事件流。战后单位分析采用外部完整战报，日志负责比赛发现和结束触发。

### BATrace 接口

以下保留最初采用 BATrace 的实测依据。现行路径是游戏数据源优先、BATrace 补充／回退；字段映射、缺口与缓存策略统一维护在[数据源参考](../reference/batrace-api.md)。

站点：`https://bot.batrace.top`。以下 GET 路径均在前序检查取得成功响应。

| 接口 | 数据 |
|---|---|
| `/api/players/info?stbid=…` | 玩家资料、总体统计、近期比赛 ID |
| `/api/players/matches?stbid=…&offset=…&limit=…` | 分页比赛摘要 |
| `/api/match?matchid=…` | 完整战报和单位实例 |
| `/api/units` | 单位名称、国家、分类、基础价格等 |
| `/api/dek/specializations` | 专精 ID、名称、国家等 |

玩家资料可包含 ELO、排名、等级、Steam ID、胜负与离场、击杀和损失价值、占点、补给、地图次数、专精等级与经验、专精组合经验及更新时间。部分玩家 `statInfo` 为空，界面按字段完整程度展示。

测试玩家的比赛列表 `totalCount` 为 100，分页有效。可回溯范围尚待确认；本地持续归档用于累积长期历史。

战报包含比赛时间、地图、胜方、双方得分，以及玩家的赛前后 ELO、出兵价值、回收价值、占点和补给等统计。单位实例包含 `Id`、`OptionIds`、`SpawnTime`、`DeathTime`、`KilledCount`、伤害和补给消耗，并可能包含回收、空投、自毁和转交信息。

实测比赛 `9765617` 返回 10 名玩家、819 条单位实例。原型缓存中 274 份比赛详情有 273 份包含单位数据；这些缓存属于原型已查询过的样本，覆盖率不能直接外推到全部比赛。

部分请求出现过 403，调整请求头后成功。新客户端需使用清晰的应用标识，区分限流、权限或校验响应、网络失败和未收录状态，并采用退避与缓存回退。请求频率及站点允许的接入方式需在正式接入前确认。

### 计时基准

41 场普通进入比赛的样本中，BATrace `StartTime` 比日志 `Scenario controller loaded` 晚 58.118～59.825 秒，中位数为 59.176 秒。候选方案为场景加载完成后加约 60 秒，对应准备阶段结束；正式采用前与游戏画面倒计时同步校准。

按比赛 ID 保存开始时间、来源和提醒状态。实时等待使用单调时钟，持久记录使用 UTC 时间；重新连接时恢复原有时间基准。无法确认起点时允许手动校准。战后可使用权威战报时间修正历史记录。

## 技术方案

| 层级 | 当前选择 | 职责 |
|---|---|---|
| 桌面外壳 | Tauri＋Rust，暂定 | 窗口、托盘、快捷键、应用生命周期 |
| 前端 | 建议 Vue 3＋TypeScript＋Vite | 主窗口、Overlay、设置和玩家详情；最终框架待定 |
| 图表 | 建议 ECharts | 趋势、排行、堆叠图和单位时间线 |
| 业务 | Rust | 日志解析、API 查询、状态管理、计时和统计 |
| 存储 | 建议 SQLite | 档案、备注、比赛、缓存和设置 |
| 皮肤 | 内置的 CSS 变量组，见 [ADR-0014](../adr/0014-skins.md) | 统一界面与图表颜色、字体、圆角；个人调整之后在内置皮肤上叠加 |

首版按 Rust 后端规划，Python 源码作为移植参考。若后续确认存在值得保留的复杂 Python 模块，再评估 sidecar 的收益。

数据流：游戏日志 → Rust 对局状态 → 玩家资料查询与 SQLite → 前端更新；比赛结束 → 战报重试获取 → 归档与统计 → 战后详情。

Rust 向前端发送当前比赛、玩家摘要、查询进度和提醒事件。完整战报按需读取，避免反复把全部单位实例发送到 Overlay。

### 窗口与资源策略

- Overlay 保持紧凑，提供锁定穿透与解锁交互两种明确模式；展开时显示玩家摘要。
- 主窗口承载完整档案、历史、备注编辑和图表；按需加载较重内容。
- 先支持整窗穿透；局部按钮可点击且其余区域穿透的行为另行验证。
- 提醒由后台触发，窗口显示时保持游戏焦点。原型快捷键可作为默认候选，支持修改与冲突提示。
- 主题首版聚焦配色、透明度、字体和间距，开放程度随着实际需求扩展。
- 统计与查询在后台执行；Overlay 计时每秒更新，减少持续动画、大面积模糊及闲置图表渲染。
- 资源评估统计完整进程树，包括 WebView2 子进程；指标包含空闲 CPU、内存、GPU 占用及游戏帧时间。具体预算在同机测试后制定。

## 存储与统计口径

建议将可过期的 API 缓存与用户长期数据分开管理。概念上包括玩家档案、备注、相遇记录、比赛摘要、原始战报、单位目录和提醒状态，实际表结构在开发时确定。

玩家使用游戏内部 ID 关联，Steam ID 作为附加身份字段；比赛使用 match ID 去重。记录获取时间、来源及数据完整程度。开局先展示已有资料并后台更新，结束后重试拉取战报，再更新相关玩家档案。备注由用户维护，API 更新只影响外部资料。

| 指标 | 计算与展示要求 |
|---|---|
| 常用单位 | 同时展示实例数、使用场次数与统计范围 |
| 兵种构成 | 结合单位分类与 role；火炮和防空、坦克和运输车分别处理 |
| 出兵节奏 | `SpawnTime` 相对比赛开始时间，按时间区间聚合 |
| 生存时长 | 仅对具有合理出生与死亡时间的实例计算，缺失死亡时间单独处理 |
| 补给倾向 | 区分自身消耗、盟友受益、从盟友获取等字段 |
| 出兵价值 | 玩家总价值使用战报字段；单单位配置成本需解析选项及版本，基础价格只能用于明确标记的估算 |
| 专精熟练度 | 使用专精与组合经验、等级 |
| 近期专精使用率 | 待获得逐场选择或验证推断方法后加入 |

实例归属需检查 `TransferredUnits` 与 `UnitData` 的关系；合并时按比赛内实例 ID 去重，并区分原始出兵、接收与转交。回收、运输、空投、缺失数值和默认省略字段需要建立明确口径，资料缺失与数值零分别保存。

统计默认显示样本场数与时间范围，并考虑比赛模式、地图、时长与游戏版本。现有数据适合出兵与战绩图表；位置轨迹和逐次攻击事件需要额外来源才能支持空间热力图或详细交战回放。

## 可行性验证与推进顺序

| 顺序 | 验证项目 | 通过依据 |
|---|---|---|
| 1 | Overlay 实机兼容 | 在目标显示模式、多屏及 DPI 下可见、穿透正确、快捷键可恢复交互，展开与提醒保持预期焦点 |
| 2 | 计时校准与重连 | 对照屏幕倒计时确定起点；重连和重启后时钟连续，提醒只触发一次 |
| 3 | 数据更新延迟 | 记录结束到战报可用的时差，识别空结果、部分结果和最终结果，确定重试策略 |
| 4 | 单位与专精口径 | 对照几场战报确认转交、空投、回收和分类；确定逐场专精能否取得 |
| 5 | 资源占用 | 比较仅 Overlay、打开主窗口、打开图表和后台统计四种状态的进程树与帧时间 |

完成关键验证后，建议依次实现：对局识别与玩家查询 → 基础 Overlay 和提醒 → 长期档案与备注 → 战后单位图表 → 多场风格与皮肤。测试应覆盖真实日志回放、重连、空名字、文件切换、接口失败和重复战报，而界面与游戏覆盖效果通过实机验收。

尚待决定的事项：前端最终框架、提醒声音与呈现方式、历史数据保留及导出策略，以及首版支持的比赛模式。可先围绕 5v5 排位完善体验，其他模式通过状态识别和标签保留扩展空间。

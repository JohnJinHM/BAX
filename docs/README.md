## 每个事实只写在一处

同一件事只在一份文档里维护，其他地方链接过去。

| 内容 | 归属 |
|---|---|
| 产品范围、推进顺序、数据来源的实测数值 | 项目规划 |
| 模块边界、数据流、目录结构 | 架构文档 |
| 做出某个选择的理由和备选方案 | ADR |
| 验证的环境、方法、原始数据和结论 | 验证记录 |
| 字段含义与统计口径的精确定义 | `reference/` |

验证得出新的数值时写进验证记录。规划里的同一数值改成指向该记录的链接，或者直接更新并注明出处。

## 写作约定

- **语言。** 正文用中文。代码标识符、日志原文和接口路径保持原样。
- **文件名。** 目录和文件名用小写英文加连字符，例如 `project-plan.md`。ADR 用 `NNNN-标题.md`，验证记录用 `NN-标题.md`，编号与验证项对应。
- **文档头。** 标题下一行写状态和更新日期，例如 `状态：草案 · 更新：2026-11-16`。状态取值为草案、生效、归档。ADR 有自己的状态取值，见 [adr/README.md](adr/README.md)。
- **链接。** 仓库内用相对路径。引用代码时链接到文件，不复制大段代码。
- **图。** 流程图、时序图和状态图用 Mermaid 写在 Markdown 里，随文本一起审阅。VS Code 预览需要安装仓库推荐的 Mermaid 扩展。截图放在 `assets/`。
- **数值。** 实测数值写明样本量、日期和取得方式，区分实测结果与推断。
- **隐私。** 文档和样本里不出现其他玩家的真实 ID 与名称。需要举例时使用脱敏后的值。

## 什么时候更新

- 代码改动使文档不再准确时，在同一次提交里更新文档。
- 模块边界或技术选型变化时，新增 ADR，再更新架构文档。
- 完成一项可行性验证时，写验证记录，更新 [validation/README.md](validation/README.md) 的状态，并处理它影响到的 ADR 和架构文档。
- 范围或推进顺序变化时，直接修订项目规划；修订历史由 git 保留。
- 文档不再适用时，把状态改为归档并在开头注明替代文档，不删除文件。

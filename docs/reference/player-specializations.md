# 上场／本局专精与使用场次

状态：生效 · 更新：2026-11-23

悬浮窗在选图／选卡（`waitingRoom`）阶段显示“上场专精”，进入加载时用约 220ms 动效收起，部署与对局期间保持隐藏。比赛结束后显示“本局专精”，直接读取本场战报的识别结果。等待战报或组合未确定时留空；旁观者不显示专精。动效遵循悬浮窗设置与系统减少动态效果选项。

当前对局详情始终保留专精列：比赛结束前显示上场组合，结束后切换为本局组合。`MatchReportView.specs` 按玩家 ID 提供本场结果，读取结果时校验比赛 ID，切换比赛与关闭视图后丢弃迟到响应。

玩家详情以图标、名称和横向柱状图展示最近最多 20 场已有战报的专精场次，标明样本数与成功识别数。只有唯一组合计入场次；“上场”取最近已有战报的结果。

## 数据口径

`statInfo.specExp`、`combinedSpecsExp` 是经验进度，存在封顶，不能用来排列使用频率。当前资料与战报样本中没有直接提供逐专精场次或所选组合的字段。

引擎读取战报原始出兵单位，用随应用发布的单位—专精可用性表枚举同国两专精组合。只有全部已知单位约束得到唯一组合时才计数。目录外单位不参与约束；只有目录外单位、多个可行组合或互相冲突时均不出结果。转交单位按原出兵者归属，避免把队友赠送的单位算入专精。每场可给两个专精各计一次，因此专精场次数之和通常为已识别场次的两倍。

目录版本为游戏 1.2.2.1，来源为 BA-Units 的 `Specializations`、`SpecializationAvailabilities` 与中文本地化表；图标使用 BA-DeckEditor 的同名游戏资源。数据在 `crates/bax-engine/src/spec-units.json`、`specializations.json` 和 `public/spec-icons/`，更新游戏版本时同步更新。游戏数据变化可能影响历史战报识别。

长期库第 6 版按玩家和比赛索引原出兵单位的类型。升级时逐场读取旧战报，新战报和索引在同一事务内保存。资料页和悬浮窗读取最近 20 场的单位类型，用当前目录推断专精。归档或替换战报后，只刷新该场新旧名单涉及的玩家。

## 请求预算

先完成已有玩家资料查询，再由独立后台任务读取资料中的 `last_fights_data`，每名敌方仅取最近一场；不请求比赛列表。OCR 无歧义候选可以触发，正式名单出现后复用本场预算；未匹配成功的玩家不阻塞其他已解析玩家。队友不触发补查。

- 每局最多 5 次额外战报请求，串行执行，每次完成后间隔 1 秒。
- 相同比赛 ID 去重；已有战报直接使用，不占请求次数。
- 发生错误（含限流）后，本局停止补查；离开比赛或断线取消正在进行的补查。
- 战报写入现有长期库，通过快照更新图标与个人页；不创建虚构的同场记录。
- 个人页只统计已有战报，不为图表批量拉取历史。

五份均未缓存时，完成时间约为五次接口耗时加四至五秒间隔；图标逐个到达。PvE 暂停这项补查。

## 资料刷新

资料按字段递归合并：缺失、null、空白字符串保留旧值，取得的新值更新。数值 0 与 false 有效，数组以新数组替换（包括空数组）。较旧响应不覆盖新资料；非法 JSON 不落库。评分历史按合并后的数值记录，避免字段缺失造成虚假变化。

实现见 [specs.rs](../../crates/bax-engine/src/specs.rs)、[spec_worker.rs](../../crates/bax-engine/src/spec_worker.rs)，验证见[专精战报与资料合并](../validation/player-specs-history.md)。

# ADR-0004：业务状态只存在于 Rust，窗口通过快照和事件订阅

- 状态：提议
- 日期：2026-11-16
- 相关：[总体架构·前后端通信](../architecture/overview.md#前后端通信)、[项目规划·窗口与资源策略](../planning/project-plan.md#窗口与资源策略)

## 背景

规划建议采用两个窗口：紧凑的 Overlay 和承载完整档案与图表的主窗口，二者共享同一份后台状态。两个窗口各自运行在独立的 WebView 里，主窗口按需打开，WebView 也可能被重新加载。一场比赛的完整战报可以有数百条单位实例（实测一场为 819 条），不适合反复发送给 Overlay。

## 决定

- 当前比赛、玩家摘要、计时和提醒状态只由 Rust 一侧的对局会话维护。会话是唯一的写入者，所有输入按消息顺序处理。
- 窗口加载时用命令取得快照，之后订阅事件。快照和事件带递增的修订号，窗口发现修订号不连续时重新取快照。
- 事件只携带当前比赛、玩家摘要、查询进度和提醒。完整战报和历史数据由主窗口通过命令按需读取，聚合在 Rust 里完成。
- 对外请求带上发起时的比赛 ID，返回时比赛已切换的结果直接丢弃。
- 通信类型以 Rust 定义为准，TypeScript 类型由它生成。

## 后果

- 两个窗口看到的状态一致，任何一个窗口关闭、晚开或重新加载都不影响业务状态。
- 前端不需要自己的持久化和网络层，Overlay 可以保持很小。
- 所有界面操作都要经过一次前后端调用。界面上的即时反馈（例如输入备注）由前端先行显示，再由后端结果确认。
- 新增界面数据时要先在 Rust 一侧定义类型和命令。

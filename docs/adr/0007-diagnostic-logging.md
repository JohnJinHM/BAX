# ADR-0007：诊断日志写入本机文件，分享时导出脱敏副本

- 状态：已采纳
- 日期：2026-11-17
- 相关：[ADR-0003](0003-workspace-layout.md)、[ADR-0004](0004-state-ownership.md)、[ADR-0005](0005-storage-separation.md)、[总体架构·诊断日志](../architecture/overview.md#诊断日志)、[0.2 实机验收清单](../guides/acceptance-0.2.md)

## 背景

**名词。** “日志”在本项目里已经指游戏写出的日志文件。BAX 自己为排障写出的记录在本文和代码里一律叫“诊断日志”，模块名 `diag`，避免两者混淆。

**发布版的诊断输出全部丢失。** 桌面应用的发布版是 GUI 子系统（`src-tauri/src/main.rs` 的 `windows_subsystem = "windows"`），没有控制台。0.2 的订阅器只写标准错误，所以现有的 warn 与 error 在用户机器上没有去处，panic 也不留痕迹。

**现有埋点只覆盖失败分支。** 0.2 全仓库约 30 处 `tracing` 调用，几乎都是 warn 级的“保存失败”“读取失败”，没有 info 级的生命周期记录。出了问题时无法从记录里复盘：读的是哪个日志文件、比赛在什么时刻进入哪个阶段、计时基准来自哪里、提醒为什么没响。

**这些问题正是实机验收要回答的。** [0.2 验收清单](../guides/acceptance-0.2.md)要求记录计时与画面的差值、提醒是否只触发一次、断线重连后计时是否连续、悬浮窗显示时游戏是否失去焦点。这些现象只发生在玩家正在游戏的时候，事后靠回忆不可靠。

**前端错误不可见。** 界面运行在 WebView2 里，发布版没有开发者工具，前端的异常无从得知。

**隐私。** 引擎处理的数据含其他玩家的 ID 与名称。0.2 的一行 debug 日志（`bax-batrace` 客户端的“请求失败”）把带 `stbid` 的请求路径原样写出。诊断日志要给开发者看，必须事先定好什么能写、分享前怎么处理。

**约束。** `bax-core` 不做 IO；基础库不依赖 Tauri（ADR-0003）；本机工具链是 Rust 1.88，新增依赖要能在这个版本上编译。

## 决定

### 埋点与输出分开

- 各库继续只用 `tracing` 的宏埋点，不安装订阅器。
- `bax-core` 不埋点，保持纯函数。跟踪器把变化作为 `Update` 交出，由引擎记录；阶段与连接的变化由引擎比较前后状态得出。
- 订阅器的装配、文件写入、滚动清理、panic 钩子和导出放在 `bax-engine` 的 `diag` 模块。桌面应用与 `bax` 命令行在启动时调用 `diag::init`，得到一个句柄，用来切换档位和在退出前刷盘。
- 不新增 crate。引擎增加 `tracing-subscriber`、`chrono` 和读取 Windows 版本用的 `winreg`，三者都已在 workspace 里。不引入 `tracing-appender` 和 JSON 输出。

### 输出位置

| 程序 | 诊断日志文件 | 标准错误 |
|---|---|---|
| `bax-app` 发布版 | 写 | 无 |
| `bax-app` 开发版（`npm run tauri dev`） | 写 | 写，档位与文件相同 |
| `bax` 命令行 | 默认不写；加 `--diag-file` 时写 | 写，与 0.2 相同 |

文件放在 `<数据目录>\diag\`，默认是 `%LOCALAPPDATA%\BAX\diag\`，随 `BAX_DATA_DIR` 一起改变。

### 文件与滚动

- 每次启动一个文件，名为 `<程序>-<启动时间>-<进程号>.log`，例如 `bax-app-20261117-203015-4120.log`。一次运行对应一个文件，用户报告“昨晚那一局”时容易找到。
- 单个文件写满 8 MB 后接着写 `….1.log`、`….2.log`。第一个点之前的部分是运行名，导出时靠它把各段归到一起。
- 整个目录不超过 64 MB 或 30 个文件，超出时从最旧的文件删起。清理在启动时和每次换文件时进行，不删除当前正在写的文件，也不动子目录。
- 诊断日志与缓存库一样可以随时整体删除，不属于 ADR-0005 所说的长期数据，自动清理不违反该决定。
- 写入由后台线程 `bax-diag` 完成，记录通过容量 4096 的通道交给它。通道满时丢弃新记录并计数，恢复后写一行“丢弃了 N 条”。日志线程和对局会话不会因为写盘而阻塞。没有新记录时每 0.25 秒把缓冲写到磁盘一次。

### 格式

一行一条记录，UTF-8，不带颜色控制符：

```text
2026-11-17T20:31:02.417+08:00  INFO match{match_id=900001}: bax_engine::session: 比赛阶段变化 from=Loading to=Deployment event=ScenarioLoaded log_time=2026-11-17 20:31:02.390 live=true
```

- 时间用本机本地时间并带时区偏移，精确到毫秒。游戏日志也是本地时间，两边可以直接对照。
- 字段用 `键=值`，没有值的可选字段整个省略。字段名是约定的一部分，脱敏依赖它们，见下文“隐私”。
- 每个文件开头是以 `#` 开头的运行信息：一句分享提醒，程序名、版本、构建类型与 git 提交，Windows 版本，进程号，启动时间，诊断档位。桌面应用另加 WebView2 版本、数据目录和启动参数。git 提交由引擎的 `build.rs` 在编译时写入，取不到时记为 `unknown`。续写的分段开头再写一遍。

### 档位

| 级别 | 用于 | 量的预期 |
|---|---|---|
| error | 功能失效，需要用户处理；panic | 正常运行时为零 |
| warn | 可以恢复的异常、降级、重试后仍失败 | 偶发 |
| info | 生命周期与状态变化 | 每场比赛几十行；空闲时每小时不超过几行 |
| debug | 每次请求、每个实时事件、每次决策的依据 | 每场比赛几百行 |
| trace | 补读的每个事件、每次快照发布 | 只在开发时临时打开 |

| 档位 | 过滤规则 |
|---|---|
| 标准（默认） | `warn,bax=info,bax_ui=warn` |
| 详细 | `warn,bax=debug` |

`EnvFilter` 按前缀匹配 target，BAX 所有成员的 target 都以 `bax` 开头，所以一条 `bax=` 就能覆盖全部；其他库只记 warn 及以上。

档位的来源，优先级从高到低：

1. 环境变量 `BAX_LOG`，语法同 `EnvFilter`，可以开到 trace。设置后档位锁定，界面上不能再改。
2. 桌面应用的启动参数 `--verbose`：本次运行使用“详细”，同样锁定。
3. 界面设置 `ui.diag`，内容是 `{"level":"standard"}` 或 `{"level":"verbose"}`。它和 `ui.hotkeys` 一样由引擎保存和分发、由外壳解释；外壳在快照里看到它变化时切换档位，立即生效，不用重启。启动后读到设置之前的几行按标准档位记录。
4. 默认为“标准”。

命令行的标准错误依次看 `BAX_LOG`、`RUST_LOG`，都没有时只输出 warn 及以上，与 0.2 相同。

### 必须记录的内容

除特别标注外都是 info。比赛相关的记录都在 `match{match_id=…}` span 内，按比赛 ID 过滤就能拿到一场的全部记录。

| 范围 | 记录 |
|---|---|
| 启动与退出 | 运行信息；引擎启动耗时与游戏日志目录的来源（启动参数、设置、自动定位）；数据库结构升级；缓存库重建（warn）；对局会话的启动与结束；桌面应用的启动与退出 |
| 游戏日志读取 | 使用的目录及来源，自动定位时记尝试次数；打开文件时记路径、大小和是否补读；补读完成时记事件数和耗时；截断（warn）；读取失败（warn，相同错误只记一次）与恢复 |
| 游戏日志事件 | 实时事件记类型与游戏日志里的时间戳（debug）；补读事件同样记录（trace） |
| 对局生命周期 | 发现新比赛（阶段、是否重连进入）；阶段变化与连接变化，记前后状态、触发事件的类型与游戏日志时间戳，由计时推进时记为“计时”；名单已知（人数、两队各几人）；比赛被取代；比赛结束（原因）；与房间断开（原因）；识别出本机玩家 |
| 计时 | 计时基准的设定，记来源、开局时刻、旧来源和移动的毫秒数；从长期库恢复的基准；手动校准的输入、旧来源与移动量 |
| 提醒 | 每条规则在本场的结果（触发或错过）、规则时间和相对预定时刻晚了多少毫秒；提醒规则更新；外壳的响铃与显示悬浮窗 |
| 资料请求 | 每次请求的玩家与排队数、每个结果的耗时与错误分类（debug）；比赛切换后到达的结果（debug）；被限流（warn）与恢复；每场比赛汇总一行请求数、成功数、各类失败数和平均耗时 |
| 外壳 | 悬浮窗显示、隐藏、锁定及触发方式（快捷键、托盘、界面、提醒、启动）；快捷键注册结果，失败为 warn；悬浮窗所在的显示器、缩放与显示器数量（debug）；显示悬浮窗前与 0.3 秒后的前台程序文件名（debug）；主窗口打开；命令被拒绝的原因 |
| 前端 | 未捕获的异常、未处理的 Promise 拒绝、Vue 渲染错误，target 为 `bax_ui`（warn） |
| panic | 线程名、位置和消息（error），刷盘后再交给默认钩子。开发版另记回溯；发布版去掉了符号，回溯只有地址，不记 |
| 运行摘要 | 详细档位下每 5 分钟一行 debug：当前游戏日志文件、玩家数、排队与在途请求数、快照修订号 |

前端不写文件。前端把错误通过命令 `report_ui_error` 交给外壳，每个窗口每分钟最多记 20 条，多出的只计数。命令失败由外壳在命令一侧记录，前端不再重复上报。这只是转交错误文本，不涉及业务状态，不违反 ADR-0004。

### 隐私

- **名称不进诊断日志。** 玩家名称、本机昵称和卡组名在任何级别都不写。游戏日志事件只写类型和时间戳，需要原文时按时间戳到游戏日志里查。
- **ID 只出现在约定字段里。** 玩家 ID 只用 `player` 和 `self_player` 两个字段，比赛 ID 只用 `match_id`，值为原始数字。请求路径和 URL 不进诊断日志，改记端点类别，例如 `endpoint=players.info`。
- **本机文件保留原值。** 诊断日志和游戏日志在同一台机器上，敏感程度相同。开发者在本机排障时需要用原始 ID 对照 BATrace。
- **分享时用导出。** “导出诊断包”把最近几次运行的文件（默认两次）按时间顺序合成一个文本文件。合并时做三项替换：`player` 与 `match_id` 字段换成本次导出内一致的代号 `P01`、`M01`；出现在 `self_player` 里的 ID 一律换成 `SELF`；路径里 `Users` 下一级的目录名换成 `%USERNAME%`。导出文件写到 `<数据目录>\diag\export\`，最多保留 10 个，完成后在资源管理器里选中它。
- **测试守住约定。** 引擎的 `diag_privacy` 测试用虚构的名字、卡组名和 ID 跑一整场比赛并截获全部诊断输出，断言名称没有出现、ID 只出现在约定字段里、导出的诊断包里一个 ID 也不剩。脱敏本身另有单元测试。

### 入口

- **设置页**新增“诊断”卡片：诊断日志目录及“打开目录”按钮，详细程度（标准、详细），“导出诊断包”按钮。档位被锁定时显示锁定的原因。外壳状态 `AppStatus` 增加诊断目录、锁定原因和写入失败的原因。
- **托盘菜单**增加“打开诊断日志目录”。
- **命令行**增加全局参数 `--diag-file`，以及 `bax diag path`（列出目录和文件）与 `bax diag export [--runs N] [--out 文件]`。

## 后果

- 发布版第一次有了可以事后查看的记录。验收时出现问题，可以附上诊断包，不再依赖回忆。
- panic 会被记录。0.2 的发布版里引擎任务崩溃是静默的。
- 按比赛 ID 过滤可以复盘一场比赛：阶段变化、计时基准的每次变动、每条提醒的结果。
- 引擎多了三个依赖和一个后台写线程。基础库不受影响，`bax-core` 仍然不依赖 `tracing`。
- 磁盘占用最多 64 MB，详细档位下写满得更快，最旧的记录被更早删除。
- 脱敏依赖字段命名约定，靠测试和代码审查维持。新增埋点时：玩家 ID 只放 `player` 或 `self_player`，比赛 ID 只放 `match_id`，不写名称、卡组名、URL 和游戏日志原文。这条规则写在 `CONTRIBUTING.md` 和 `CLAUDE.md` 里。
- 字符串字段用 `%` 以 Display 写出，避免带引号；可选字段用 `Option` 包装的 `tracing::field::display` 或 `debug`，没有值时整个字段省略。

## 备选方案

- **用 `tracing-appender` 滚动文件。** 它只按时间滚动，没有单文件大小和目录总量的上限，也不提供“每次启动一个文件”。本机依赖缓存里也没有它。自己写的写线程加滚动清理代码量小，规则可控。
- **JSON Lines 格式。** 机器处理方便，但验收时用记事本直接阅读更重要。脱敏只依赖几个固定字段名，文本格式足够。JSON 输出还要多引入 `tracing-serde`。
- **新建 `bax-diag` crate。** 边界更清楚，但调用方只有两个，导出需要知道数据目录的布局。先放在引擎的模块里，出现第三个调用方时再拆。
- **专门的设置项 `diag.level`，由引擎解释。** 引擎要新增命令并把档位放进快照。档位只有外壳和命令行用得到，沿用 `ui.` 前缀、由外壳解释，与快捷键设置的做法一致，引擎不用改。
- **写进 SQLite。** 排障时数据库本身可能就是出问题的部分；诊断日志也不该和长期数据混放（ADR-0005）。
- **Windows 事件日志或 `OutputDebugString`。** 用户需要专门的工具才能取出，不便于附在反馈里。
- **写入时就脱敏。** 分享更省事，但开发者本机排障时失去了对照 BATrace 的能力。导出时再脱敏，两边都能满足。
- **前端自己写文件。** 需要给 WebView 开文件系统权限，多出一处写入点，格式和滚动也要再做一遍。

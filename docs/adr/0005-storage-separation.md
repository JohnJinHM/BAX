# ADR-0005：长期数据与缓存分成两个数据库文件

- 状态：提议
- 日期：2026-11-16
- 相关：[总体架构·存储](../architecture/overview.md#存储)、[项目规划·存储与统计口径](../planning/project-plan.md#存储与统计口径)

## 背景

原型的 `Cache` 把所有数据放在一起，并在初始化时删除超过 7 天的记录。这种清理只适合缓存。BAX 要长期保留玩家备注、相遇记录和已归档战报，规划建议把可过期的接口缓存与用户长期数据分开管理。BATrace 比赛列表的可回溯范围尚未确认，规划靠本地持续归档来累积长期历史，归档丢失后不一定能重新获取。

## 决定

使用两个独立的 SQLite 文件：

| 文件 | 内容 | 规则 |
|---|---|---|
| 长期库 | 备注、设置、提醒配置；玩家档案、相遇记录、比赛摘要、原始战报；单位与专精目录；计时基准、提醒触发状态、待归档比赛 | 没有任何自动过期或批量删除；表结构迁移前先备份 |
| 缓存库 | 短期的接口响应 | 可以按时间清理，也可以整个删除，应用随后能照常启动 |

单位目录和专精目录放在长期库。归档的战报靠它们解读，目录随游戏版本变化后，旧战报仍然需要当时的条目。

## 后果

- 清理缓存的代码拿不到长期库的连接，误删备注和归档的路径在结构上不存在。
- 备份和导出只需要处理长期库这一个文件。
- 出现缓存损坏或数据异常时，删除缓存库是安全的排障手段。
- 两个库之间不能直接联表。目前没有这样的需求；将来出现时由 `bax-store` 在代码里组合，或者把相关数据移入长期库。

## 备选方案

- **一个数据库，用表区分缓存和长期数据。** 部署更简单，但清理逻辑和长期数据共用一个连接，隔离只能靠代码约定。原型的问题正是出在这里。

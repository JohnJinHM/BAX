# 选图选卡阶段的玩家来源

状态：草案 · 更新：2026-11-18

## 已确认的原因

当前游戏版本 1.2.2.1 的 `Room: (WaitingRoom|…), Client: (名字|ID)` 不是加入通知。对本机 `GameAssembly.dll` 与 `global-metadata.dat` 的只读静态分析确认：

- `NetworkRoomService.OnOutgoingClient` 格式化这条消息并调用 `UnityEngine.Debug.Log`。
- `OnIncomingClient` 也构造相同格式的字符串，但没有把它交给普通日志；其 `Debug.Log` 调用输出的是 `Client name - …`，并受对局房间分支限制。
- `OnEnterInInstance` 恢复房间状态后按房间类型分支，等待室跳过 `Player list:` 的输出。完整名单在转入对局房间后写出。

本次二进制内的方法 RVA 分别为 `OnIncomingClient=0x62cba0`、`OnOutgoingClient=0x62d9c0`、`OnEnterInInstance=0x62bb70`。`Debug.Log` 调用点位于 `0x62ced0`（加入，输出名字）、`0x62dcbd`（离开，输出身份线索）、`0x62c1e1`（完整名单）。这些地址仅对应本机此次构建；文件 SHA-256 与分析脚本保存在本机验证目录中。

本机旧版 Unity `Player.log` 的 12 条同格式记录均有 `OnOutgoingClient(RemoteClient)` 调用栈，与当前静态结果相符。该文件最后修改于 2025-12-15，不能作为当前实时数据源。

因此，BAX 提前显示的玩家是日志碰巧暴露的身份线索，不能推断成“陆续加入的完整名单”。这些 ID 仍可用于预取资料，最终以 `Player list:` 为准。

## 实测

2026-11-17，用 `bax logs pregame --all` 回放本机 915 份日志：562 个同时有等待室进入事件和正式名单的记录（跨文件未去重；受现有解析器支持格式限制）。按**开始加载之前的线索与后来正式名单的交集**计数：

| 提前覆盖人数 | 记录数 |
|---|---:|
| 0 | 493 |
| 1 | 49 |
| 2 | 16 |
| 3 | 2 |
| 4 | 2 |

当晚两场 5v5 的等待室分别记录 1 人和 0 人，正式名单均为 10 人。后一场等待室持续约 47 秒，没有玩家线索；选图完成后的正式名单正常解析。查询当时仍在进行的比赛战报，BATrace 返回未收录。这一次结果不能证明接口对所有比赛都不可提前查询。

组队大厅还会输出 `Incoming client … to lobby`，但它属于组队大厅，不是这场比赛的双方名单。当前未将其直接并入对局，避免把离队、换大厅或匹配取消后的玩家带入下一场。

原始日志、核查表和静态分析输出保存在本机 `.local/pregame-20261117/`，不入库。静态分析只读取磁盘文件，未附加或修改游戏进程。v39 元数据布局参考 [irea 的 IL2CPP 说明](https://github.com/ihotfix/irea/blob/main/docs/il2cpp-metadata.md)，解析脚本只用于本机验证。

## 已实施的核查与修复

- `bax logs pregame [文件] [--dir 目录] [--all]`：列出等待室、加载与首次名单时间，加载前线索数、被跟踪器接收的 ID 数、正式名单人数和覆盖情况；只读日志，不访问网络。
- `bax logs watch` 的实时事件带游戏日志时间，便于对照画面。
- 详细诊断记录每条房间玩家线索的 ID、接收结果和忽略原因；标准诊断在正式名单到达时记录覆盖人数。ID 沿用 ADR-0007 的字段约定。
- 修复独立的流式名单缺陷：一轮空闲或补读到文件末尾时只发布已收到的部分，不再关闭名单记录。后续玩家行到达后发布累计名单，真正的记录边界才关闭记录。回归测试覆盖实时空闲及启动补读两条路径。这能修复加载阶段漏行，不能凭空补出等待室里未写出的玩家。

## OCR 初测与尚待验证

下一场在选图、选卡画面核对可见昵称、数字 ID 和队伍布局，评估本地 OCR。现机 Windows OCR 有英文、简体中文和日文识别语言。实测 BATrace 名称搜索接口可用，但本机昵称搜索就出现了仅大小写不同的另一个账号，且返回的资料时间早于当前对局。若画面只有昵称，必须另行解决同名、截断、改名和 OCR 错字的问题；不能把模糊搜索的第一个结果直接当成玩家身份。

在本机隔离环境试验 [RapidOCR](https://github.com/RapidAI/RapidOCR) 3.10.0、ONNX Runtime 1.32.0、PP-OCRv6 small，CPU 限为 2 个计算线程。对本次**加载画面**的 10 个昵称区域进行裁剪、3 倍放大与对比度处理：严格字符一致 8/10，忽略空白差异后 9/10；另一个将 ASCII 字母识别成带变音符号的字母，置信度仍为 0.98471。单次调用约 14.08 秒（尚未区分冷启动与稳定耗时）。Windows OCR 在同样区域的中日文漏字与错字更多。

这只是 1 张加载画面的样本，不是选图阶段验收，不能据此宣布 OCR 达标。截图和模型仅用于 `.local/` 内的验证，没有成为生产依赖，也未上传图像。不能仅靠 OCR 置信度自动认定玩家身份。

目前未接入自动 OCR，选图阶段全员识别尚未完成。

## 2026-11-18：昵称与等级匹配、预热耗时复测

按用户指定，仅使用昵称和等级选择候选账号，不使用 ELO。以用户提供的一张 3576×1987 加载倒计时截图做离线验证；截图没有提供对应的权威数字 ID，本次只能判断候选是否明确，不能计算真实身份匹配正确率。

### 方法与耗时

沿用 RapidOCR 3.10.0、ONNX Runtime 1.32.0、PP-OCRv6 small，在 AMD Ryzen 7 9800X3D 上 CPU 推理、2 个计算线程、1 个 inter-op 线程。模型文件已下载，保持同一进程与模型实例，剔除每组第一次调用后统计。区域坐标根据这张截图手工确定，尚未实现自动定位与其他分辨率适配。

| 流程 | 预热后次数 | 中位耗时 | 最小～最大 |
|---|---:|---:|---:|
| 原初测的十昵称拼图，沿用检测、方向分类与识别 | 5 | 0.204 秒 | 0.197～0.213 秒 |
| 新截图十昵称＋十等级，裁剪、2 倍放大、拼图、检测与识别，关闭方向分类 | 10 | 0.381 秒 | 0.337～0.409 秒 |
| 新截图初版裁剪直接批量识别，跳过检测 | 10 | 0.194 秒 | 0.179～0.211 秒 |

原流程本次首次调用为 0.575 秒；修正裁剪的新流程另起进程，首次调用为 0.622 秒。先前的 14.08 秒未复现，不能断言差额全部由冷启动造成。原 PNG 解码另测约 0.072 秒；表中不包含屏幕采集、窗口定位、网络查询与 UI 更新。直接识别虽然更快，却漏掉连字符、末尾字母，当前优先保留检测。

### OCR 与查询结果

- 修正等级区域，排除 `lvl` 尾部后，10 个等级全部与人工读图一致。初版会把 73 读成 173，说明裁剪边界是实质性准确率因素。
- 10 次预热后调用输出一致；重复同一张图不是 10 个独立准确率样本。
- 昵称中 8 个可清楚辨认的字符串与人工读图一致；1 个全小写昵称被识别成大写；1 个末尾呈方框，无法仅凭截图确定原始字符。没有对应日志核对俄文同形字，本截图也不含可用于验证的日文昵称。
- 使用 OCR 原始名字查询 `/api/players/search?q=...&limit=50`，十次 GET、三并发，总墙钟耗时 3.442 秒。网络只发送查询文字，不上传截图；响应保存在本机验证目录。此数字是一次实际网络测量，不是延迟分布。
- 8 个槽位有较明确的首选候选：包括同名候选等级分别为 57、70，而画面等级为 57 的情况，等级能直接帮助排序。单个明确首选候选与画面等级仍可能相差 3～10 级，因此等级不能要求严格相等。
- 1 个槽位有大小写不同、等级同为 100 的两个候选。若将 OCR 的精确大小写匹配置于最高优先级，会偏向与画面小写形式不符的账号。该槽位应保留歧义，不把排序第一解释成身份已确认。
- 1 个含方框的名字未搜到候选。

### 结论与下一步

昵称＋等级的候选排序可行，当前瓶颈主要在名称查询，OCR 预热后约 0.38 秒。匹配应把大小写等 OCR 常见混淆作为候选歧义处理，再利用等级距离排序；等级相同且名称仅有视觉混淆时不能强行确认。ELO 不参与匹配。

下一轮用实际选图选卡截图与随后日志名单配对，统计首选候选准确率、歧义率与提前量，并验证俄文、日文及混合昵称。当前实验没有接入生产会话，也没有修改长期玩家记录。

复测脚本、逐次计时、裁剪图与原始候选响应在 `.local/ocr-20261118/`：`benchmark.py`、`match_probe.py`、`benchmark.json`、`corrected-benchmark.json`、`matching.json`。`review_matching.py` 对已有响应按 NFC＋casefold 名称比较及等级差重排，结果在 `matching-reviewed.json`，并列首选明确标为歧义，没有再次请求网络。脚本是本机可行性探针，未入库；原初测的模型和环境继续使用 `.local/pregame-20261117/`。


## 2026-11-18：开发分支接入

分支 `codex/pregame-ocr-candidates` 已接入桌面程序：本地昵称/历史别名与等级优先，在线候选补充，日志 ID 接管；设置可关闭。正式候选视图不进入长期比赛名单。设计见 [ADR-0008](../adr/0008-pregame-ocr.md)。

自动定位采用左右画面区域内的等级行与邻近昵称，不使用本次截图的十个手工坐标。对同一截图复测，含中英日模型、俄文备选识别分支的预热后 5 次中位 1.033 秒，范围 1.027～1.093 秒；十个槽位全部找到、十个等级与人工读图相同。本图未产生俄文备选，不能据此认定俄文实景准确率。计时包含区域 OCR 和备选识别，不包含屏幕采集、网络与“两帧一致”的等待时间；原始记录在 `.local/ocr-20261118/integrated-extract.json`。

已验证工作进程启动协议、模型预热和 stdin 关闭后的退出；本机运行环境安装在用户数据目录。自动测试覆盖等级消歧、大小写平手、Unicode、同一 ID 的别名去重、重复槽位、历史别名查询、搜索参数编码、候选不写比赛记录、日志替换、换局、关闭与重新开启功能后忽略旧结果。主窗口与窄悬浮窗以虚构数据完成浏览器渲染检查。

仍待实际游戏验收：前台窗口截图在不同显示模式下是否可用，真正选图/选卡布局覆盖率，悬浮窗遮挡，帧时间影响，以及与随后日志逐人比较的候选正确率。截图离线测试和回放测试不能替代这一轮。
